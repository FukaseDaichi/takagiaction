それぞれ対応（修正する / 仕様として容認する）が決まり次第、結論を docs/ に反映して本ファイルを削除する。

## 1. イントロを途中で飛ばすと、ターミナルの文体設定が壊れたまま残る

`terminal.ts` の `terminal_line_wait`（1 行あたりの待ち）と `terminal_print_ident`（`> ` プレフィックス）はモジュール変数で、`terminal_run_garbage()` が 16ms / なし に変え、続く `terminal_run_story()` が 100ms / あり に戻す。

`main.ts` はクリックで `terminal_cancel()` を呼んでイントロのチェーンをその場で打ち切るため、**ノイズ表示の開始からストーリー表示の開始前（ノイズのタイピング中＋その後の 1.5 秒の間）にクリックすると、戻す側が永久に走らない**。以後そのセッションのすべての通知（深度到達、ロック解除、予備の一本、音声トグル、非常口通過）が `> ` なし・16ms/行の早送りで表示され続ける。

- 進行への実害はない: `terminal_show_notice()` が返す秒数も同じ `terminal_line_wait` から計算されるため、降下演出の長さ（通常 約 5.2 秒 → 約 2.5 秒）は表示と一致したまま縮むだけ。
- ただし「クリックでイントロを飛ばす」は自然な操作なので、発生頻度は低くない。
- 修正案: `terminal_show_notice()` の冒頭（または `main.ts` のクリックハンドラ）で 2 変数を通常値（100 / true）に戻す。

## 2. AudioContext を resume() しておらず、自動再生ポリシーで無音になる恐れ（要実機検証）

`audio.ts` はモジュール初期化時（＝ユーザー操作前）に `new AudioContext()` し、コードのどこにも `resume()` が無い。Chrome 等の自動再生ポリシーでは、ユーザー操作前に生成した AudioContext は `suspended` 状態で始まり、**ユーザー操作があっても自動では再開されない**（ページ側がジェスチャハンドラ内で `resume()` を呼ぶ必要がある）。該当すると BGM・効果音が一切鳴らない。

- 開発中に気づきにくい理由: localhost / 127.0.0.1 では既定ミュート（`audio_enabled` の初期値）なので、そもそも音を期待しない。また作者の環境では Media Engagement Index により自動再生が許可されて音が出ている可能性があり、その場合は新規訪問者だけが無音になる。
- 検証方法: 本番 URL をシークレットウィンドウ（MEI の影響を排除）で開き、クリック後に BGM が鳴るか確認する。
- 修正案（該当した場合）: `audio.ts` に `audio_ctx.resume()` を呼ぶ関数（例: `audio_unlock()`）を足し、`main.ts` の初回クリックハンドラ（既存のユーザー操作起点）から呼ぶ。

## 3. ヒーロー画像 2 枚で約 4.7MB（初期ロードの支配項）

`m/hero.png`（約 2.33MB、イントロ背景）と `m/ui/hero.png`（約 2.35MB、死亡画面イラスト）で、JS バンドル本体（54KB）やアトラス（数十 KB）に対して桁違いに重い。GitHub Pages での初回表示と、初回の死亡画面（＝自席の端末。起動直後にも出る）の表示を遅らせる。

- ゲーム進行への影響はなく優先度は低い。
- 表示サイズ（フルスクリーン背景／左パネル背景）に対して解像度・色数が過大であれば、縮小やインデックスカラー化（減色 PNG）で 1/5 以下にできる見込み。
